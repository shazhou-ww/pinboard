# 发布项与指针设计

本文是 [Idea.md](./Idea.md) 的同世界 supporting
document，整理本轮讨论的产品语义、技术建议及风险，不是独立契约，也不表示已经授权实施或部署。具体 API、表结构和界面在实施阶段再细化。

## 已对齐的方向

内容继续静态、公开、按 CID 寻址；在内容之上增加可选的发布项，用可变指针跟踪版本。可变的是当前指向，不是内容字节。

用户有两种发布入口：

1. 从已有 Pin 选择一个发布项，将该 CID 添加为新版本。
2. 上传时直接指定发布项，后台先完成上传，再创建版本并切换指针。

用户有两种发布项访问方式：

1. 发布项稳定链接访问当前生效版本。
2. 指定版本链接访问固定版本。

原来的 CID 分享链接继续有效。普通用户仍可只上传、保存和分享 Pin，不必预先创建发布项，也不因普通上传自动更新线上内容。同一 CID 可以被多个发布项引用。

用户指出发布项访问天然适合协商缓存；采用协商缓存作为公开可变响应的默认方向，而不是默认禁用缓存。

补充的 UI 方向是发布项与静态 Pin 都使用统一尺寸卡片，并用可辨识的方式表达发布项的多版本属性。下文将同墙混排、徽标文案和交互建议展开，具体视觉样式尚未定稿。

本轮明确：首版覆盖 Web、CLI、HTTP 和 MCP 全部入口；版本历史对所有人统一公开；发布当前 CID 为 NOP，发布非当前的历史 CID 则创建新版本。删除通过最近删除机制统一提供默认一个月的恢复窗口，本文按 30 天描述；普通 Pin 的 Unpin 和发布项删除均适用，不再另设一套撤销与立即释放流程。

## 现有业务边界

当前 [README](../../../../../../README.md)、
[PinService](../../../../../../apps/worker/src/service.ts) 和
[存储说明](../../../../../../docs/storage.md) 表明：

- 上传验证 CID 哈希和完整 DAG 后，发布不可变 CAR 与索引。
- Pin 是账户引用，账户内名称和列表私有；上传字节公开，包括失败写入可能留下的字节。
- 修改 Pin 名称不改变 CID；Unpin 仅移除账户引用。
- 最后一个有效引用消失后，内容才有资格进入七天宽限期后的清理；共享 CAR、队列及失败可延长保留。
- 没有任意远程 CID 抓取、IPNS 发布或动态网站执行能力。

扩展不能把 Pin 的 CID 改成可修改字段，也不能把 Pin 名称隐式变成公开发布标题。

上述 Unpin 后立即移除引用是现有行为。本构想有意将其改为先移出正常列表、进入最近删除，30 天保留期结束后才释放该账户引用；公开 CID 与其他有效引用的语义不变。

## 概念模型建议

### 本轮更新：item 身份、内容引用与节点描述

2026-11-06 的讨论在已上线能力上增加以下要求，本文原有首轮方案及证据背景不代表这些增量已实现。

- 固定 Pin 和 publication 都属于 pinned
  item，名字绑定 item，而非底层 CID 或某次来源卡片。publication 保持自己的名字，不因发布新内容而继承来源 Pin 名称。
- 数据节点的描述部分有两个并列、可选且来源不同的字段：用户编写的 `description`
  与系统生成的
  `preview`。它们共同描述节点，description 不是 preview 缓存的附属品，也不等同于版本更新日志。
- 固定 Pin、publication 各版本引用的节点及目录内部节点沿用该描述概念。重建、失败、替换或清理 preview 只能更新对应系统字段，不能覆盖或删除用户 description；编辑 description 不要求重建 preview。
- 实际文件字节或目录条目中的名字属于内容，不等于 item 的展示名字，不能在 link 或重命名时顺带修改。

例如固定 Pin「草稿 A」引用 CID-A，publication「项目周报」引用 CID-B；把前者加入后者后，publication 新版本引用 CID-A，仍叫「项目周报」，来源 Pin 仍叫「草稿 A」。描述与预览随节点引用解析，而来源 item 的名字不随引用传播。

### 卡片定向拖放与显式转换

| 来源与目标                         | 确认后的行为                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| 外部文件拖到空白区域               | 保留普通上传、仅 Pin / 创建 publication / 发布到已有项的选择                               |
| 外部文件拖到 publication 卡片      | 明确目标并确认，先上传成功，再将内容发布为该项的新版本                                     |
| 外部文件拖到固定 Pin 卡片          | 提示转为 publication，原固定内容为 v1，拖入内容为 v2；确认公开名字，不把文件名当作目标标题 |
| 已有固定 Pin 拖到 publication 卡片 | link 到已保存内容，按现有规则新增版本或 NOP；不重复上传、不移动、不删除或隐藏来源 Pin      |
| 固定 Pin 菜单「转为 publication」  | 无需上传，以原内容创建 v1，原位置展示 publication；确认原 item 名字将成为公开名字          |

拖入时高亮实际目标，确认框清楚说明操作对象、将要建立的版本及公开信息。取消不修改原 item 或 publication；文件上传成功但后续发布失败仍按既有部分成功规则保留 Pin、显式报错。提供菜单/键盘/触屏等价入口，不要求用户必须拖拽。自拖放或不支持的载荷不隐式发布；目录沿用已有上传能力，不借本轮擅自扩展批量文件映射规则。

link 和转换是不同操作：link 保持两个独立 item；转换是用户明确要求的原位升级，不默认在墙上重复展示原静态卡片。转换必须保护原 CID 分享链接及引用存活，不把 UI 替换理解为立即删除内容或放弃恢复保障。后端是否沿用原记录或用新发布身份替换属于实现选择，不承诺复用 CID 作为 publication
ID。

已有 Pin
link 到 publication 继续遵循当前 CID 为 NOP、非当前历史 CID 创建新版本的规则。名字变更不会改变 CID，publication 的名字不会被来源名字覆盖。转换时允许保留自身名字，但必须先明确公开含义，不能把私有名称未经确认泄漏为公开标题。

### 描述模型尚需实施前明确的设计项

本轮确认的是逻辑归属及独立字段，不是物理编码方案。不得将前期建议中的「新建描述 DAG 节点」「改描述就改变 CID/自动创建版本」当作用户已选择的规则。实施前须明确并在实现契约记录：

1. description 是与内容关联的持久元数据还是实际编码入 DAG；仅凭内容 CID 导出时是否携带描述，如何兼容原始文件/CAR。
2. 相同 CID 在不同账户、item、publication 版本及目录路径中的描述作用域、公开范围与写权限；不默认允许一次编辑改写其他账户或历史版本的说明。
3. 描述发布后如何编辑、是否快照及如何追溯；描述单独更新是否形成新版本，以及它与既有 CID-NOP、ETag 和固定历史的关系。

这些是待明确的设计项，而非放弃节点描述要求。普通内容发布的 NOP、独立引用与当前生产数据兼容性在新规则明确前保持不变。

| 对象                  | 作用                       | 变化规则                |
| --------------------- | -------------------------- | ----------------------- |
| Pin / CID             | 账户保存的一份具体内容     | 内容不变，账户标签可改  |
| Publication（发布项） | 同一持续发布物的稳定身份   | 独立于名称的稳定 ID     |
| Revision（版本）      | 一次发布记录，绑定一个 CID | 版本与 CID 的绑定不可改 |
| Ref（指针）           | 指向某个发布版本           | 经鉴权和并发控制后更新  |

第一阶段每个发布项仅提供 current。数据关系为发布项拥有多条版本记录，current 指向其中一条；以后有实际需求再扩展 stable、preview 等渠道，不先做分支系统。

发布项使用随机、不随标题改变的 ID，不使用邮箱或账户私有标签作为永久地址。友好别名留待后续。

### 版本序号与指针变更序号分离

“最新”在稳定入口中指当前生效版本，不等于最大版本号。发布到版本 5 后回滚至版本 3：

- current 指向版本 3，版本 4、5 仍存在。
- 指针变更序号继续单调递增。
- 再次发布新内容产生版本 6，不复用版本号。

版本记录与指针操作记录分别表达发布历史和切换历史。回滚不覆写旧版本绑定。

### 重复 CID 与 NOP

在同一原子发布操作中比较目标与 current 的规范化 CID，而不是仅比较输入字符串：

- 目标就是当前 CID：返回明确的 NOP 结果，不创建版本、不切换 current、不递增指针变更序号，不改变发布更新时间。
- 目标不同于当前 CID：创建下一个新版本并切换 current；即使历史中已有相同 CID，也不复用旧版本号。
- 显式回滚仍是切换到指定旧版本，与重新发布历史 CID 创建新版本不同。

并发前置条件与幂等检查仍先于该判断；旧预期序号不能通过 NOP 绕过冲突。同一幂等请求重试返回原结果，不因 current 后续变化而重新执行，包括原结果为 NOP 的情况。

## 两种发布入口的共同流程

上传并发布是组合入口，不是修改已有内容：

```text
上传并验证完整内容 → 得到 CID → 检查/预览 → 创建版本与保留引用 → 切换 current
```

已有 Pin 发布从获得已保存 CID 的阶段进入相同服务。预览生成可异步，完整内容必须已成功发布、可读，才能切换指针。

第一阶段建议仅接受调用者账户中已 Pin 且完整可用的目标，不接受任意外部 CID 或 URL 并假定其存在。

发布的关键写操作应在一个 D1 原子事务中完成：

1. 检查账户归属、发布权限、目标引用及存储可发布状态。
2. 校验预期指针变更序号。
3. 按当前 CID 判断 NOP，或创建版本、保留引用及操作记录。
4. 非 NOP 时切换 current 并递增变更序号。

检查不能仅发生在事务外；必须与 Unpin、清理声明等并发操作协调。R2 与 D1 不是分布式事务，沿用先准备不可变内容、后提交发布状态的顺序。

两个客户端基于同一变更序号发布时，只允许一个成功，另一个显式收到冲突，例如 409，不能静默最后写入覆盖。回滚使用同样的控制。

支持幂等键，响应丢失后的重试不重复创建版本；同一幂等请求应可确认原结果，不同负载复用键应明确冲突。

上传失败或发布事务失败都不能移动当前指针。上传成功但发布失败时，保留已上传的 Pin，明确提示“上传成功、发布失败”，允许重试发布，不把部分成功伪装成完整成功，也不通过删除公共对象补偿。

## 访问与下载建议

建议路由形状如下，最终命名待实施确定：

```text
/p/<publicationId>       当前生效版本
/p/<publicationId>/v/3   固定发布版本
/share/<cid>            既有固定内容分享入口
```

公开页面展示已明确公开的发布标题、当前版本、更新时间、实际 CID，并分别提供复制跟随链接、固定版本链接和 CID。说明跟随链接可变化，引用或验证应使用固定版本。

同一有效发布项的版本历史和固定版本对所有人统一公开，不区分登录状态、所有者与访客的读取结果；历史列表提供固定版本入口。不额外公开账户身份或私有 Pin 标签，管理写操作仍须鉴权。

下载先解析一次发布项并锁定实际 CID，再完成整个下载；不能对目录内每个文件分别解析 current，以免混合多个版本。

不使用永久重定向表达可变指针，也不把当前 CID 嵌入一个不经验证的长期缓存响应。

当前网关提供原始块、缩略图和 CAR，并非任意 HTML 网站托管。新增发布项不自动增加路径网关、任意 HTML 执行或用户脚本嵌入，沿用现有安全边界。

## 协商缓存

将可变的发布状态和不可变的内容分层：

| 响应                                 | 建议策略                                           |
| ------------------------------------ | -------------------------------------------------- |
| 公开的发布项解析、current 状态       | Cache-Control: public, no-cache，配合 ETag         |
| 确认不可变的公开版本内容或 CID 内容  | 长缓存，配合 immutable                             |
| 可能修改或撤销的版本页面、公开元数据 | 按其响应变化协商缓存，不因版本固定就默认 immutable |

no-cache 允许保存，但每次复用前必须重新验证，不等于 no-store。第一阶段不设置可直接复用旧指针的正数新鲜期，也不默认允许 stale 回退。

请求带 If-None-Match 时，未变化返回 304；发布、回滚或响应元数据变化后返回新表示与 ETag。304 不发送正文，但仍需读取当前轻量状态以验证。

指针响应的 ETag 建议基于单调递增的变更序号，而不只用 CID：即使回滚到旧 CID，也能识别发布状态变化。标题等公开字段、表示格式或页面生成版本变化，必须反映到对应表示的 ETag；不能把不同表示共用的状态序号直接当作所有强 ETag。

先确认发布项仍存在且公开有效，再判断条件请求；进入最近删除后，当前入口、固定版本和历史接口均不可继续公开解析，也不得以旧 ETag 返回 304。恢复后原发布 ID、版本号和链接保持不变，删除与恢复状态变化须反映到可变表示的校验标识。私有管理接口不能复用公开缓存策略。

长缓存内容无法被发布项删除召回，这与现有公共 CID 语义一致。关闭发布入口不代表已经下载或缓存的内容消失。

## 内容保留与 GC

这是新增模型最重要的完整性风险：当前存活判断主要认识账户 Pin，只新增指针表会导致仍在发布的内容被清理。

建立两个独立的保留来源：

```text
账户 Pin ─────────┐
                  ├─ 保留目标 CID 及完整 DAG
发布版本保留引用 ─┘
```

确定的生命周期：

- 普通 Pin 的 Unpin 将该账户 Pin 移入最近删除，正常列表不再展示；30 天内保留内容与预览引用并允许恢复。该操作不删除或关闭引用相同 CID 的发布项。
- 发布项删除将整个发布项连同全部版本移入最近删除，关闭其当前入口、固定版本入口和公开历史；30 天内仍保留全部版本引用。删除中的发布项不能发布或回滚，恢复后才可继续操作。
- 保留期内恢复 Pin 或发布项，保留原身份、标签或标题、版本历史和 current，不创建发布版本；发布项恢复后原链接重新可用。
- 默认保留期为删除时间起 30 天，列表展示到期时间；重复删除已删除对象不得无提示延长保留期。恢复与到期释放须原子协调，到期后不再承诺可恢复，即使后台清理尚未运行。
- 到期后释放该 Pin 的账户引用，或该发布项全部版本的保留引用；不释放其他账户、其他 Pin 或其他发布项的引用。有效发布项默认保留全部历史，不在首版额外引入单版本删除或立即永久删除能力。
- 最近删除的 30 天恢复窗口与底层现有七天 GC 宽限期不同；只有到期释放后最后一个有效引用消失，才启动七天宽限期。因此不是“第 30 天保证物理删除”，也不保证召回公开 CID、缓存或外部副本。

最近删除列表与恢复操作属于账户管理能力，不是公开发布历史的一部分。首版全部入口共用相同的删除、查询最近删除、恢复和到期语义，不能让 CLI、HTTP 或 MCP 的 Unpin 绕过恢复窗口。

实施必须覆盖完整 DAG、CAR
manifest 与物理对象的存活判断、清理声明及重检、最后无引用时间、预览与缩略图保留。发布引用的增加、释放须与相应时间戳和清理护栏原子协调，不能只在 cron 最外层加一次查询。

保持当前完整 CAR 存储方式，不为发布项顺手引入差量归档、全局去重或 CAR 压缩整理。

## 权限、公开范围与信任

本轮不增加访客、登录用户或所有者之间的发布历史读取权限差异，不扩展为私有发布系统。管理操作继续遵守账户归属和既有会话、Token 授权边界；新增发布写能力的具体 scope 名称在实施时确定，不使既有 pins:write
Token 自动获得修改稳定链接的能力。

所有发布、回滚、删除、最近删除查询和恢复操作鉴权；有效发布项的当前、固定版本和历史解析无需登录。保留现有会话、Origin 校验、Token 撤销过期和 MCP
OAuth 资源边界。

创建发布项时明确说明稳定入口、发布标题和完整版本历史公开；Pin 私有标签和账户身份不随之公开。所有人读取相同的公开版本历史，不另设访客受限视图。

CID 验证的是内容字节，不证明作者身份或“作者最新发布”。第一阶段指针真实性由 Pinboard 的 HTTPS 与账户授权承担。若以后需要平台外独立验证，再评估签名发布记录或 IPNS，而非现在引入密钥托管、续签和分布式传播。

## 产品落点与分期建议

第一阶段确定完成以下闭环：

- 从已有 Pin 创建发布项、添加版本，上传时选择发布项。
- 发布后切换 current，统一公开版本历史、回滚，以及 Pin 和发布项的最近删除与恢复。
- 当前 CID 重发为 NOP；非当前 CID 即使曾发布过也创建新版本。
- 跟随链接、固定版本链接及协商缓存。
- 引用保留、授权、并发控制和幂等与功能一并交付。
- Web、CLI、HTTP、MCP 全入口交付，共用发布与最近删除服务，不分批遗漏客户端或各自定义语义。

Web 可从 Pin 菜单的“创建发布项”和发布项详情的“发布新版本”起步，不必重做整个内容墙；卡片展示方向见下节。

第二阶段再评估 CI 自动发布、多渠道、友好别名、细粒度凭据和签名记录。不做任意远程 URL 跟踪、指针套指针、实时协作编辑或动态代码执行。

尚待实施细化的内容是 API 与写权限名称、版本标签、保留成本的展示，以及卡片徽标的具体样式和筛选入口。重复 CID、公开历史、30 天最近删除及全入口交付已确定，不再列为待定选择；不引入未经确认的保留额度或付费方案。

## UI：统一卡片，轻量区分发布项

### 相同的外形，不同的身份

发布项和静态 Pin 使用相同尺寸、比例、间距和信息条结构。现有内容墙是响应式网格，卡片为 4:3，底部有磨砂信息条；沿用这一基础，不因版本数增加高度，也不将发布项强制放入另一种列表。

建议默认同墙混排；需要时再提供“全部 / Pin
/ 发布项”的筛选，而不是要求用户在两个独立管理页面之间切换。不同屏幕可响应式调整列数和宽度，“统一尺寸”指同一布局下两类卡片使用同一规格，不要求所有设备固定像素宽度。

每个发布项只占一张卡片，历史版本在详情中展开，不在内容墙为每个版本额外生成发布卡片。静态 Pin 继续代表固定 CID；发布项卡片代表稳定发布身份，不能仅按当前 CID 合并卡片。

### 建议的可见信息

| 区域     | 静态 Pin 卡片           | 发布项卡片                         |
| -------- | ----------------------- | ---------------------------------- |
| 主预览   | 固定 CID 的现有安全预览 | current 指向 CID 的同类安全预览    |
| 类型标识 | 保留现有轻量外观        | 常显的小型图层图标和“发布项”标识   |
| 底部名称 | 账户 Pin 名称           | 发布项名称                         |
| 辅助信息 | 当前内容大小            | 当前内容大小、当前版本和历史版本数 |
| 更多操作 | 现有菜单                | 发布项专属菜单                     |

发布项辅助信息例如“当前 v3
· 共 5 个版本”。回滚到 v3 后仍可有 5 个历史版本，不能把“共 5 个版本”当成“当前 v5”。即使仅有一个版本，也保留发布项身份标识，避免首次迭代后卡片突然变成另一种对象。

徽标应是小而常显的身份提示，不依赖 hover、颜色、动态动画或只有 tooltip 的图标；触屏和键盘用户同样能够辨识。可用轻微的叠层视觉强化多版本含义，但叠层只作装饰，不能扩大布局占位、遮住邻卡或与目录卡片的文件夹造型混淆。不通过整张卡片换主题色或增加大段说明区分。

版本徽标与右上角现有更多按钮避让；长名称、长版本文案不撑大卡片。详细版本信息放入详情，辅助技术能够读取发布项类型、当前版本和总版本数。

### 点击、复制与管理

- 点击静态卡片，仍打开现有 Pin 详情；点击发布项卡片，打开发布项详情，默认展示 current，并提供版本历史入口。
- 发布项详情明确区分跟随链接、固定版本链接和当前 CID；版本切换可以查看历史，不应仅因查看历史就更新 current。
- 发布项菜单建议提供“查看详情”“复制发布项链接”“发布新版本”“版本历史”和“移入最近删除”；回滚和删除等重要操作在明确上下文中完成。
- 静态 Pin 保留“复制链接”“复制 CID”“Unpin”，并增加“添加到发布项”的入口，其中可创建新发布项或选择已有项。
- Pin 的 Unpin 和发布项的删除都进入最近删除，但确认文案须明确操作对象，以及发布项删除会关闭其全部公开解析入口、期满释放全部版本引用；不能暗示删除源 Pin 会同时删除发布项。
- 发布项的默认链接复制动作建议复制跟随链接；如果沿用现有 CID 胶囊，必须仍明确表示并复制当前 CID，不可让同一外观静默变成另一种复制对象。

### 预览与状态

发布或回滚成功后，卡片身份和尺寸保持稳定，更新其 current、版本信息及预览来源。标题取发布项名称，不能被新上传文件名无提示覆盖；预览仍按实际源 CID 复用，不另外复制一份发布项内容。

加载新预览期间可使用同尺寸占位；若暂时保留旧预览，必须明确说明它是旧版本，不能把旧图片与新版本号组合成已更新的假象。预览 pending、unsupported 和 failed 沿用现有区别，预览失败不等于发布失败。

无法解析或目标读取失败时，卡片保持占位并显式展示状态。已删除的 Pin 和发布项移出正常内容墙，统一在账户最近删除列表展示类型、删除时间、到期时间和恢复操作；删除中的发布项不能继续伪装成正常公开入口。

### Pin 与发布项同时存在

普通发布或 link 不会自动移除、隐藏或转换源 Pin。默认允许两者同时出现，通过身份标识区分固定内容和持续发布入口；一个 CID 被多个发布项引用时，各发布项仍是独立卡片。用户明确选择「转为 publication」时例外：按本轮转换要求原位升级，不在墙上默认重复显示源静态卡片。

这样不改变现有账户引用和 Unpin 的心智模型。若以后确实出现重复感，再评估明确可控的筛选或分组，不以隐式去重隐藏用户已有 Pin。

### 后续视觉验证重点

在桌面、窄屏、触屏和键盘路径下，对照静态 Pin 与单版本、多版本、回滚、预览异常的发布项卡片，确认尺寸一致、类型可辨、当前版本与版本总数不混淆、徽标和菜单不遮挡、固定与跟随链接不会误复制。本轮仅记录设计，不修改产品 UI 或声称已完成视觉验证。
