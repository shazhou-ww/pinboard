# 发布项与指针设计

本文是 [Idea.md](./Idea.md) 的同世界 supporting document，整理本轮讨论的产品语义、技术建议及风险，不是独立契约，也不表示已经授权实施或部署。具体 API、表结构和界面在实施阶段再细化。

## 已对齐的方向

内容继续静态、公开、按 CID 寻址；在内容之上增加可选的发布项，用可变指针跟踪版本。可变的是当前指向，不是内容字节。

用户有两种发布入口：

1. 从已有 Pin 选择一个发布项，将该 CID 添加为新版本。
2. 上传时直接指定发布项，后台先完成上传，再创建版本并切换指针。

用户有两种发布项访问方式：

1. 发布项稳定链接访问当前生效版本。
2. 指定版本链接访问固定版本。

原来的 CID 分享链接继续有效。普通用户仍可只上传、保存和分享 Pin，不必预先创建发布项，也不因普通上传自动更新线上内容。同一 CID 可以被多个发布项引用。

用户指出发布项访问天然适合协商缓存；采用协商缓存作为公开可变响应的默认方向，而不是默认禁用缓存。

## 现有业务边界

当前 [README](../../../../../../README.md)、
[PinService](../../../../../../apps/worker/src/service.ts) 和
[存储说明](../../../../../../docs/storage.md) 表明：

- 上传验证 CID 哈希和完整 DAG 后，发布不可变 CAR 与索引。
- Pin 是账户引用，账户内名称和列表私有；上传字节公开，包括失败写入可能留下的字节。
- 修改 Pin 名称不改变 CID；Unpin 仅移除账户引用。
- 最后一个有效引用消失后，内容才有资格进入七天宽限期后的清理；共享 CAR、队列及失败可延长保留。
- 没有任意远程 CID 抓取、IPNS 发布或动态网站执行能力。

扩展不能把 Pin 的 CID 改成可修改字段，也不能把 Pin 名称隐式变成公开发布标题。

## 概念模型建议

| 对象 | 作用 | 变化规则 |
| --- | --- | --- |
| Pin / CID | 账户保存的一份具体内容 | 内容不变，账户标签可改 |
| Publication（发布项） | 同一持续发布物的稳定身份 | 独立于名称的稳定 ID |
| Revision（版本） | 一次发布记录，绑定一个 CID | 版本与 CID 的绑定不可改 |
| Ref（指针） | 指向某个发布版本 | 经鉴权和并发控制后更新 |

第一阶段每个发布项仅提供 current。数据关系为发布项拥有多条版本记录，current 指向其中一条；以后有实际需求再扩展 stable、preview 等渠道，不先做分支系统。

发布项使用随机、不随标题改变的 ID，不使用邮箱或账户私有标签作为永久地址。友好别名留待后续。

### 版本序号与指针变更序号分离

“最新”在稳定入口中指当前生效版本，不等于最大版本号。发布到版本 5 后回滚至版本 3：

- current 指向版本 3，版本 4、5 仍存在。
- 指针变更序号继续单调递增。
- 再次发布新内容产生版本 6，不复用版本号。

版本记录与指针操作记录分别表达发布历史和切换历史。回滚不覆写旧版本绑定。

## 两种发布入口的共同流程

上传并发布是组合入口，不是修改已有内容：

```text
上传并验证完整内容 → 得到 CID → 检查/预览 → 创建版本与保留引用 → 切换 current
```

已有 Pin 发布从获得已保存 CID 的阶段进入相同服务。预览生成可异步，完整内容必须已成功发布、可读，才能切换指针。

第一阶段建议仅接受调用者账户中已 Pin 且完整可用的目标，不接受任意外部 CID 或 URL 并假定其存在。

发布的关键写操作应在一个 D1 原子事务中完成：

1. 检查账户归属、发布权限、目标引用及存储可发布状态。
2. 校验预期指针变更序号。
3. 创建版本、保留引用及操作记录。
4. 切换 current 并递增变更序号。

检查不能仅发生在事务外；必须与 Unpin、清理声明等并发操作协调。R2 与 D1 不是分布式事务，沿用先准备不可变内容、后提交发布状态的顺序。

两个客户端基于同一变更序号发布时，只允许一个成功，另一个显式收到冲突，例如 409，不能静默最后写入覆盖。回滚使用同样的控制。

支持幂等键，响应丢失后的重试不重复创建版本；同一幂等请求应可确认原结果，不同负载复用键应明确冲突。

上传失败或发布事务失败都不能移动当前指针。上传成功但发布失败时，保留已上传的 Pin，明确提示“上传成功、发布失败”，允许重试发布，不把部分成功伪装成完整成功，也不通过删除公共对象补偿。

## 访问与下载建议

建议路由形状如下，最终命名待实施确定：

```text
/p/<publicationId>       当前生效版本
/p/<publicationId>/v/3   固定发布版本
/share/<cid>            既有固定内容分享入口
```

公开页面展示已明确公开的发布标题、当前版本、更新时间、实际 CID，并分别提供复制跟随链接、固定版本链接和 CID。说明跟随链接可变化，引用或验证应使用固定版本。

下载先解析一次发布项并锁定实际 CID，再完成整个下载；不能对目录内每个文件分别解析 current，以免混合多个版本。

不使用永久重定向表达可变指针，也不把当前 CID 嵌入一个不经验证的长期缓存响应。

当前网关提供原始块、缩略图和 CAR，并非任意 HTML 网站托管。新增发布项不自动增加路径网关、任意 HTML 执行或用户脚本嵌入，沿用现有安全边界。

## 协商缓存

将可变的发布状态和不可变的内容分层：

| 响应 | 建议策略 |
| --- | --- |
| 公开的发布项解析、current 状态 | Cache-Control: public, no-cache，配合 ETag |
| 确认不可变的公开版本内容或 CID 内容 | 长缓存，配合 immutable |
| 可能修改或撤销的版本页面、公开元数据 | 按其响应变化协商缓存，不因版本固定就默认 immutable |

no-cache 允许保存，但每次复用前必须重新验证，不等于 no-store。第一阶段不设置可直接复用旧指针的正数新鲜期，也不默认允许 stale 回退。

请求带 If-None-Match 时，未变化返回 304；发布、回滚或响应元数据变化后返回新表示与 ETag。304 不发送正文，但仍需读取当前轻量状态以验证。

指针响应的 ETag 建议基于单调递增的变更序号，而不只用 CID：即使回滚到旧 CID，也能识别发布状态变化。标题等公开字段、表示格式或页面生成版本变化，必须反映到对应表示的 ETag；不能把不同表示共用的状态序号直接当作所有强 ETag。

先确认发布项仍存在且公开有效，再判断条件请求；撤销后不得继续以旧 ETag 返回 304。私有管理接口不能复用公开缓存策略。

长缓存内容无法被发布撤销召回，这与现有公共 CID 语义一致。发布入口撤销不代表已经下载或缓存的内容消失。

## 内容保留与 GC

这是新增模型最重要的完整性风险：当前存活判断主要认识账户 Pin，只新增指针表会导致仍在发布的内容被清理。

建立两个独立的保留来源：

```text
账户 Pin ─────────┐
                  ├─ 保留目标 CID 及完整 DAG
发布版本保留引用 ─┘
```

建议语义：

- Unpin 只移除账户引用，不隐式撤销发布，也不删除版本。
- 发布版本独立保留目标内容，不能依赖原 Pin 永远存在。
- 第一阶段默认保留所有发布版本，支持历史访问与回滚；展示版本数量及保留成本，不承诺无限免费历史。
- 后续可设计显式释放历史版本引用；仍被任一渠道指向的版本不可释放，释放后保留记录并明确标记内容不再保证可用。
- 撤销公开入口、释放发布版本引用、Unpin 是不同操作，不能混在同一个删除按钮里。撤销是否同时释放引用需另行确定并明确提示。
- 只有最后一个有效引用消失才启动现有七天清理宽限期；仍不保证精确删除日期或召回外部副本。

实施必须覆盖完整 DAG、CAR manifest 与物理对象的存活判断、清理声明及重检、最后无引用时间、预览与缩略图保留。发布引用的增加、释放须与相应时间戳和清理护栏原子协调，不能只在 cron 最外层加一次查询。

保持当前完整 CAR 存储方式，不为发布项顺手引入差量归档、全局去重或 CAR 压缩整理。

## 权限、公开范围与信任

新增独立的发布权限，不使既有 pins:write Token 自动获得修改稳定链接的能力。第一阶段可使用账户级发布权限，后续再设计单发布项或单渠道的 CI 凭据。

所有发布、回滚和撤销操作鉴权；公开解析无需登录。保留现有会话、Origin 校验、Token 撤销过期和 MCP OAuth 资源边界。

创建发布项时明确确认稳定入口和哪些元数据将公开。内容字节公开，不意味着 Pin 私有标签、账户身份和完整版本列表自动公开。固定版本的公开访问与版本历史枚举是不同能力，历史列表是否公开另行决定。

CID 验证的是内容字节，不证明作者身份或“作者最新发布”。第一阶段指针真实性由 Pinboard 的 HTTPS 与账户授权承担。若以后需要平台外独立验证，再评估签名发布记录或 IPNS，而非现在引入密钥托管、续签和分布式传播。

## 产品落点与分期建议

第一阶段建议完成小而完整的闭环：

- 从已有 Pin 创建发布项、添加版本，上传时选择发布项。
- 发布后切换 current，查看自己的版本历史、回滚、撤销入口。
- 跟随链接、固定版本链接及协商缓存。
- 引用保留、授权、并发控制和幂等与功能一并交付。
- Web、CLI、HTTP、MCP 共用发布服务，不各自定义发布语义。

Web 可从 Pin 菜单的“创建发布项”和发布项详情的“发布新版本”起步，不必重做整个内容墙。如何展示独立发布项入口，在实施时按现有界面模式细化。

第二阶段再评估 CI 自动发布、多渠道、友好别名、细粒度凭据和签名记录。不做任意远程 URL 跟踪、指针套指针、实时协作编辑或动态代码执行。

尚未定稿的细节包括 API 与权限名称、版本标签、重复 CID 的再次发布策略、撤销与引用释放的关系、保留额度、历史公开范围和发布项界面位置。上述建议保留讨论依据，不把这些选择伪装为已获用户确认的实现要求。
