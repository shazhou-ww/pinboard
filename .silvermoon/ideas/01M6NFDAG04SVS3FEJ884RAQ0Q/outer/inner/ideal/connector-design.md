# 长连接取数节点池与账号连接器：方案与待验证事项

本文支持 [构想契约](./Idea.md)。本次讨论把“公网控制面 + 取数节点池 +
R2 在线副本”作为主要方向，保留原先的账号设备连接器模式；这里只整理构想，不代表已选定完整架构、完成兼容验证或获准实施部署。沿用 idea 标识
`account-kubo-connectors`，不新建另一个 idea。

## 问题与关键判断

标准远程 pin 请求提交 CID，不传输内容字节。Kubo 可附带本地节点的
`origins`；找不到 provider、来源离线或缺块都可能失败，标准不保证任意 CID 一定可取到，也没有统一的取数超时。

Pinboard 当前只能对自身存储中已有的完整 DAG 增加账户引用，不会递归到互联网寻找缺失内容。已有的 Kubo
HTTP 读取路径解决“Kubo 从 Pinboard 下载”，不解决反向取数。

一台常在线 Kubo 可以承担取数和本地存储，但反向代理或 HTTP
Tunnel 只暴露接口，不会把 Kubo RPC 自动变成标准 Pinning Service
API，也不会自动解决 swarm 的 TCP/UDP、NAT 和 relay 连通性。直接公开完整 Kubo
RPC 不可接受。

因此，将能力拆开：Pinboard 保留公网 API、鉴权、任务状态和 R2 存储；若干运行 Agent +
Kubo 的受信任设备主动建立长连接，执行取数任务。这里的“执行 worker”不是 Cloudflare
Worker，而是可运行 Kubo 的节点。

## 两种长连接角色

| 角色                     | 解决的问题                      | 调度范围与取数方式                                               |
| ------------------------ | ------------------------------- | ---------------------------------------------------------------- |
| 取数执行节点池，主要方向 | 谁负责去 IPFS 网络把 CID 取回来 | 服务授权的节点池；选一个健康且有容量的节点，通过其 Kubo 获取内容 |
| 账号设备连接器，保留模式 | 谁已经有只存在于用户设备的内容  | 只探测请求账号授权的设备；导出其本地 DAG，不能跨账号枚举         |

两种角色可以复用控制通道的概念，但不能混淆权限。服务节点可以执行多个账号各自授权的任务，不意味着这些账号能访问节点管理接口、查看其他任务，或调度其他用户的私人连接器。

仅本地读取与允许 Kubo 联网获取是不同能力。节点池以联网取数为用途；私人设备连接器是否允许联网必须另行授权。部分 RPC 会隐式联网，需验证如何保证本地限定，不能仅凭调用位置宣称离线。

## 候选交互

```text
标准 API 客户端 / Kubo / Agent
               |
               | 提交 CID、查询状态、管理请求
               v
Cloudflare 上的 Pinboard
  公网 API / 鉴权 / 持久化任务 / 调度
               |
               | 出站连接建立的 WSS 控制通道
               v
取数节点池：Agent + Kubo
               |
               | P2P 找来源、获取完整 DAG
               | HTTPS 上传保留原始 blocks 的 CAR
               v
Pinboard 校验与入库 ---- R2 内容 / D1 引用与状态
               |
               v
公网 HTTP 按 CID 读取
```

长连接建议传任务、探测和进度，CAR 经有界 HTTPS 上传进入现有校验链路。Durable
Object 与休眠 WebSocket 是候选协调机制，具体分片、额度、费用和恢复方式尚未确定。执行程序可独立分发或作为 CLI 的可选常驻能力，不把既有 CLI 改成
`ipfs` 命令包装器，也不要求普通上传下载客户端安装 Kubo。

## 节点池的一次 Pin 流程

1. 鉴权后持久化请求并生成不透明 `requestid`，进入
   `queued`；若完整内容已在 Pinboard，校验可复用状态后可直接建立引用，不必启动取数。
2. 从健康、有容量且获授权的执行节点中选一个，授予有时限的任务租约。初期可只有一个节点；多节点时可在合格候选中随机选取，不预设复杂调度算法，也不同时让所有节点重复下载。
3. 执行节点通过本机 Kubo 使用 provider 发现、`origins` 等线索获取 DAG，进入
   `pinning`。根 block 存在不等于完整 DAG 可用；来源可能仍因 NAT、离线或缺块不可达。
4. 导出并上传完整 CAR。服务端校验任务授权、目标根 CID、各 block 哈希、支持编码和完整 DAG 闭包，遵守现有资源限制；不能下载普通文件后重编码冒充同一 CID。
5. 只有必要内容已写入 R2、索引与账户引用发布成功后才报告
   `pinned`。节点声称下载完成、本地 pin 成功或上传开始，都不是服务的成功条件。
6. 节点掉线、租约超时或取数失败时有界重试或转交其他节点；无节点时有限等待，最终不能完成则报告
   `failed` 和原因。重试预算、退避、截止时间及取消行为待定。

账号连接器模式则先对同账号在线设备有界并行探测，再选一个已有内容的来源导出上传；它不同于让任意节点去网络找数据。多来源部分 blocks 的合并不是初版承诺。

## 长连接不是可靠队列

任务状态、截止时间和归属必须持久化。休眠、断线、网络切换和服务重启不能让任务静默丢失；节点重连需要重新认证并协调未完成任务。

租约和上传授权须能区分当前有效执行与过期执行，防止转交后旧节点的迟到结果覆盖状态。重复上传、取消、删除、替换以及请求完成后的结果都应幂等处理；取消后不得意外重建账户引用。替换 pin 时还需保护旧引用，避免提前回收。

取数节点本地内容何时可以释放，需与任务完成、有效 delegate 的服务窗口及失败重试约定一致。节点本地副本不作为唯一持久化依据；R2 入库失败不能返回成功。

## 公网入口与在线副本的准确含义

- Pinboard 提供统一公网入口，执行节点无需公开自己的 Kubo 管理端口；控制通道由节点主动连入。
- 成功 pin 后，来源设备、取数节点甚至整个执行池离线，都不应阻止通过 Pinboard
  HTTP 路径读取已持久化内容；节点池离线影响新取数任务，而非已有副本。
- “在线备份”是按 CID 保存的不可变内容快照，不是持续同步文件夹、跟随修改或即时复制的承诺。文件变化产生新 CID，需要再次提交；R2 入库前仍可能失败。
- 继续遵循既有账户引用和内容保留政策，不承诺无条件永久保存、跨区域灾备或零故障 SLA。最后引用消失后的清理不因本构想改变。
- 公网 HTTP 可读不等于公共 IPFS 网络自动发现。现有显式配置的 Kubo HTTP
  retrieval 路径可用于读取；DHT 宣告、P2P 再提供和永久在线的 Bitswap 服务不是自动附带能力。

设备之间如果只是在线互传，可以直接 swarm/固定 peering，配合 agent 传递 CID；这不自动复制文件或建立访问控制，也不替代来源下线后的在线副本。Pinboard 不必参与每次设备间传输。

## 授权、安全与公开内容

- 将服务节点注册凭证、请求账号权限及任务上传授权分开，均可撤销；撤销必须影响已有连接，不能只在首次握手检查。
- 请求归属、额度和任务目标由服务端鉴权确定；跨账号执行不等于跨账号可见，私人设备连接器仍保持账号隔离。
- 只允许受限的 CID 取数、DAG 导出和任务反馈，不开放任意 RPC、shell、文件路径或 URL 代理。Kubo
  RPC 保持本地可达。
- 取数可能触发本地或私网连接；`origins`、provider 地址、资源消耗和公网滥用需要有明确的地址与预算策略，不能把受信任节点变成不受限的网络代理。
- HTTPS 上传授权绑定账号、任务、当前执行、目标 CID 和有效期。工作节点不可信的内容声明必须由服务端验证，日志不包含凭证或内容字节。
- 私人连接器启用时须明确告知用户允许读取、公开上传的范围；能读取不代表同意公开。传输加密不等于内容私有；敏感内容需在进入公开存储前加密。
- 延续现有公开内容政策，包括失败部分写入也可能公开；不承诺删除所有网络副本。

## 标准 API 与真实 delegate

仍需标准接口适配层，负责创建、列举、查询、替换、删除，以及过滤、分页、元数据和错误格式；不能把本机 Kubo
RPC 直接代理为标准接口。新增命名空间应保留现有客户端语义。

标准按 `requestid`
区分重复提交；当前账户 pin 按账号和 CID 唯一。必须定义多请求与同一引用之间的关系，以及与 CLI/Web
unpin 的交互，避免删一个请求时误删其他有效引用。

本次讨论核对的 Pinning Service API 1.0.0 schema 要求 `PinStatus.delegates`
必填且至少一个地址，语义是能通过 Bitswap 接收数据的节点。只有私人 WebSocket 或 HTTP
provider 标识不能满足该语义。

节点池引入真实 Kubo 后，可研究返回获分配节点的真实 Peer
ID 与可达 swarm 地址，使客户端和执行节点尝试建立数据通道。这改善了原先没有真实 delegate 的限制，但还不是严格兼容的证明：

- 必须验证地址实际可达、Bitswap 可用、节点在所承诺的任务窗口内在线；出站 WSS 或 HTTP
  Tunnel 本身不提供这些保证。
- API 返回时尚未分配节点、排队或转交节点时，delegate 的选择和有效期仍需定义；不能为了满足 schema 填假地址或默认填空数组。
- 需同时运行目标 Kubo 工作流实验和官方 schema 验证，明确实际版本与限制，不以客户端接受某种响应替代标准符合性结论。

## 后续需要决定，但现在不实施

1. 节点池的注册、运营责任、容量与费用；先单节点还是多节点，以及是否需要服务级与账号专属两种池。
2. 真实 delegate 的可达性、分配时机与有效窗口；目标 Kubo 版本及严格标准符合性的验收方式。
3. 离线等待、任务租约、重试、并发与大小限制；不默认放宽既有上传限制。
4. 重复请求、取消和替换的引用语义；私人连接器是否保留为初版能力以及本地限定策略。
5. 运行与分发、撤销、节点本地清理和停用流程；任何实现、部署或发布另行授权。

公共 HTTP 网关仍可作为未来独立来源，但不是本地独有内容入库的保证，也不是隐式回退方案。
