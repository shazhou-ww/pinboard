# PDF 节点缩略图技术方案

本文是 [Idea](./Idea.md)
的可行性与技术取舍说明，不是独立契约，也不表示已经实施。测试依据见[调研证据](./Research-evidence.md)；准备阶段仅约束方向和风险，参数在实施时结合完整资源测试确定。

## 目标与现有基础

目标只有一个：从源 CID 得到一张 PDF 第一页的 WebP 图片。排除完整阅读器、翻页、文本选择、公开文件 Range 接口、第三方转图服务和原始文件改写。

现有 [preview 生成器](../../../../../../apps/worker/src/previews.ts) 已能识别
`%PDF-`，目前返回
`unsupported`；已有生成版本、任务租约、重试、按 CID 发布以及旧产物保留机制。[图片模块](../../../../../../apps/worker/src/preview-image.ts)
已支持最长边 480px、最大 64
KiB 的 WebP 产物；[前端](../../../../../../apps/web/src/pin-preview.tsx)
已能显示同一描述格式的图片。

当前 primary 的源存活判定涉及 `retained_roots`
及保留 DAG 的成员，不仅是账户 pin。接入必须复用现有判定、授权和回收事务，不恢复到早期仅检查
`pins` 的实现。

## 读取模型：不是固定头部采样

普通 PDF 的索引通常在尾部，第一页的字体、图片和对象可以分散在任意位置；线性化 PDF 有利于前部读取，但不是必须条件。不能用“前若干 KiB 已读取”证明首页依赖齐全，也不能把读取失败当作空白页。

R2 中保存的是 CAR，而不是一个可直接按 PDF 偏移读取的文件：

```text
PDF 文件区间
  -> UnixFS 文件偏移和 DAG
  -> 块 CID
  -> D1 的 CAR 对象与块偏移索引
  -> R2 Range 读取完整块并验证 CID
  -> 已验证块缓存与 PDF 区间缓存
```

[存储层](../../../../../../apps/worker/src/storage.ts) 已提供块级 Range；UnixFS
exporter 的 `content({ offset, length })`
能跳过与目标文件区间无关的子树，因此不需要迁移 CAR 格式或复制一份完整 PDF。

必须区分三个指标：PDF 逻辑区间字节数、实际 R2 块读取字节数、渲染内存占用。完整块校验会放大窄区间读取，例如只需要几 KiB 也可能读取约 256
KiB 的叶块；导入 CAR 的块大小不保证与普通上传一致。

## 渲染器选择与异步衔接

优先采用 PDFium
WASM：它能直接产生像素，不要求 Workers 提供浏览器 Canvas。PDF.js 加浏览器适合阅读器，但不是本项目缩略图生成的最小方案；不引入 Browser
Run。

PDFium 的 `FPDF_FILEACCESS.m_GetBlock`
是同步回调，不能直接返回异步 R2 结果。使用渐进加载协议，而不是在回调里阻塞等待或运行时动态编译代码：

1. 同步回调只查询已缓存区间或复制已就绪的字节；`FPDFAvail_IsDocAvail`
   收集缺失区间提示。
2. 返回 JavaScript 后，按预算异步读取提示涉及的 UnixFS 区间，并校验、缓存完整块。
3. 重复检查文档可用性，获取文档，再通过 `FPDFAvail_IsPageAvail(..., 0, ...)`
   补齐第一页依赖。
4. 明确第一页可用后渲染；若仍出现未缓存读取，拒绝发布，不能用零填充数据或残缺图片兜底。

回调通过构建期预编译的 WASM 桥接模块写入 PDFium 函数表；本地 workerd 已验证此方式。避免依赖
`addFunction` 在运行时从 JavaScript 动态构造 WASM 模块。

非线性化 PDF 也已验证可局部完成；损坏索引、修复扫描或第一页重资源可能要求读取大部分乃至全部文件。渐进接口不保证必然节省 R2 数据。

## 文件策略与输出复用

建议小文件直接完整读取，大文件渐进加载，具体切换阈值在实施阶段以请求次数与读取放大测试决定，不作为本次构想的固定承诺。

两条路径使用同一份请求内块缓存与累计预算，包括识别头部时已读的数据。并发命中同一 CID 必须共享同一个读取 Promise，避免多个区间重复下载同一块；不能在切换策略后清零预算。

PDFium 仅渲染第 0 页，白底，按输出边界计算尺寸，产生 RGBA；随后直接复用像素到 WebP 编码，避免先输出 PNG 再解码。编码器与 JPEG、PNG、WebP 解码器应分开初始化，PDF 任务不应额外加载无关解码器。

输出继续是 `image/webp`
描述、独立缩略图 CID 与既有图片存储，不新增 PDF 专用数据库表。提升
`PREVIEW_VERSION`，使旧的 `unsupported`
PDF 能按原机制重新生成；保持旧产物在替换失败时的现有保留语义。

## 字体、资源和失败边界

| 项目       | 提议或已知边界                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 输出       | 最长边 480px，产物不超过 65,536 字节，沿用既有降质、缩小与失败规则                                          |
| 文件与读取 | 服从已有上传边界；沿用并验证最多 64 次块读取、12 MiB 实际块读取预算，并另设渐进轮次、逻辑缓存和等待队列边界 |
| WASM 内存  | 以已验证的 PDFium 64 MiB 线性内存上限作为候选，不把它当作整个 isolate 的上限                                |
| 字体       | 装载明确授权的回退字体；已测简繁中文和日文，当前测试字体不含韩文，不承诺所有脚本或字形                      |
| 调度       | 单 isolate 内共享原生渲染状态串行使用，队列有界；状态按任务隔离，不跨请求缓存源 PDF 字节                    |
| 超限恢复   | 观测原生分配失败、WASM abort 和同步缓存缺失；不发布残缺结果，故障实例弃用，后续任务重新初始化               |
| 时间       | `Promise.race` 不能中断同步 WASM；必须验证平台 CPU 限制和后台任务时限，不能承诺任意 PDF 的可中断超时        |

字体通过 PDFium 虚拟文件系统加载，并以正确的原生 `FPDF_LIBRARY_CONFIG`
指针指定目录。PoC 使用约 4.5
MB 的 Apache-2.0 回退字体；正式引入前必须保留授权和来源，核算字体、WASM、编码器及现有 Worker 的总包体积。

内存硬上限应来自固定版本构建产物的内存声明或原生编译配置。PoC 用 WABT 重建并验证内存最大值；正式流程应固定输入与输出校验值、验证声明，并在上游更新时重新运行等价和边界测试，不能只修改 JavaScript 变量来声称硬上限生效。

加密且需要密码的文件不接收密码输入；确定不支持的内容与损坏、源不可用、平台异常和资源超限按现有状态模型明确区分并记录原因。重试服从现有上限，不能因同一文件反复耗尽资源形成无界重试。没有缺字的图片也不能证明整份 PDF 完整，纯白页不能作为通用失败检测方法。

## 尚未被证明的上线条件

字体回退、渐进 R2 读取和像素到 WebP 分别得到验证，但完整组合尚未作为业务 Worker 接入。特别需要补齐：

- 组合后总 isolate 内存、故障实例等待回收时的峰值、多个请求和其他图片任务共存的压力。
- 线上 CPU、后台执行时限、实际部署包体积及字体覆盖与成本取舍。
- 带表单、注释、对象流、增量更新、不同层级 UnixFS 和旧独立块布局等样例；不把少量成功样例扩展成全部 PDF 的保证。

正式实施应先固化适配层和测试，再接入现有生成与发布链路；不因为本次调研通过而直接部署或放宽既有预算。
