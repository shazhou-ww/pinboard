# 系统边界与方案复审

本文是 [Idea](./Idea.md)
的架构与风险补充。2026-11-07 复审结论：PDFium 渐进加载路线可行，但两个 PoC 不能直接拼接上线。以下是设计约束与待实施验收，不表示相关问题已经通过业务代码修复。

## 架构原则：高内聚、低耦合、少侵入

只在 Worker 内部建立必要的模块边界，不预先建立插件框架、通用文件服务、新 workspace 或第二套任务系统。模块边界不等于独立部署；只有完整资源验证证明必须隔离时，才决定是否增加专用执行环境。

```text
现有 API / 上传 / 定时任务 / 公开出版物入口
                    |
            既有 preview 编排与发布
           /          |           \
  只读文件源适配    PDF 首页渲染    共享像素编码
         |            |               |
  UnixFS + 块存储   PDFium/WASM      WebP 编码器
         |            |
  既有 D1 + R2     字体/回调/原生资源
```

### 单向依赖与责任

| 边界           | 输入与输出                          | 唯一负责                                                          | 不应知道                                       |
| -------------- | ----------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| preview 编排   | 源 CID → 现有描述及图片产物         | 保留源判定、调度、租约、状态、重试、CID、发布事务、回收引用       | PDFium 指针、字体文件系统、原生回调布局        |
| 只读文件源适配 | 已授权的源 CID → 有界 `size/readAt` | UnixFS 偏移映射、完整块校验、进行中请求去重、块缓存及物理读取预算 | PDF 格式、PDFium、缩略图发布、账户标签         |
| PDF 首页渲染   | 只读文件源 → 独立 RGBA 像素         | 全读/渐进策略、逻辑窗口、第一页可用性、尺寸、内容能力检测         | `Bindings`、D1、R2、CID、HTTP 路由和数据库状态 |
| PDFium 运行时  | 一次独占渲染会话                    | 模块、字体、ABI、回调表、原生句柄、内存失败及失效隔离             | 账户、保留根、重试时刻和持久化                 |
| 像素编码       | RGBA → 有界 WebP 字节及尺寸         | 缩放、编码参数、降质与产物限制                                    | PDFium、UnixFS、存储和账户                     |

接口示意仅说明依赖，不是新增公开协议：

```ts
interface PreviewFileSource {
  readonly size: number;
  readAt(
    offset: number,
    length: number,
    signal?: AbortSignal,
  ): Promise<Uint8Array>;
}

interface PreviewRaster {
  readonly width: number;
  readonly height: number;
  readonly data: Uint8ClampedArray;
}

// 取消仅约束异步读取和阶段间检查，不能中断正在执行的同步 WASM。
// 来源与会话生命周期由调用者的 finally 管理；返回像素不引用可失效的原生内存。
```

渲染器不接收完整 `env` 或 R2 bucket，也不直接调用
`processPreview`。文件源可以用内存样例替代，渲染器可以单独测试，存储适配可以用假块源验证偏移与预算。只读边界不通过 TypeScript 类型替代原有授权：入口与编排仍必须完成当前源访问和保留状态检查。

### 最小修改面

- [生成器](../../../../../../apps/worker/src/previews.ts)：增加 PDF 分派，接入有界源与错误映射；复用图像产物发布。仅为新执行方式补充忙碌退让、预算和版本过渡，不重写既有调度系统。
- [图片处理](../../../../../../apps/worker/src/preview-image.ts)：只抽出共享的像素类型、编码初始化及像素到 WebP；原有图像识别、解码和输出行为须保持。
- PDF 适配及文件源辅助逻辑封装在内部模块中；不把 PDF 状态扩散到 storage、service、contracts、前端或公开接口。
- [块存储](../../../../../../apps/worker/src/storage.ts)、CAR 索引和数据库 schema 原则上不变。文件源使用已有
  `getBlock` 的大小与流，拒绝或超限时取消流，不靠包装、替换 R2
  binding 来收集生产统计。
- 构建依赖、WASM 校验产物、字体授权和测试样例是明确的必要改动；不将实验环境依赖、操作系统字体或会话绝对路径带入生产。

以下是计划，不是已经执行的包修改、发布或资源创建。“包”区分仓库 workspace 与第三方依赖；“部署项”指实际运行的服务、绑定和云资源；“发布项”指随版本交付的产物及分发渠道。

Worker，不新增自有 workspace、不新增生产服务、不新增 npm 发布项。**

## 复审发现与设计收敛

### R1：逻辑文件大小必须独立限制（高）

[DAG 校验](../../../../../../apps/worker/src/content.ts)按去重后的块载荷累加 32
MiB；重复引用同一叶块可以得到远大的 UnixFS 文件。复审探针用两个唯一块、1,051,786 字节载荷还原出 67,108,864 字节的文件。探针证明尺寸差异，不是一次生产上传或 PDF 渲染测试。

因此“服从上传限制”不能替代文件源检查。文件源先以 `bigint`
验证逻辑文件大小，首版采用独立的 32 MiB
PDF 逻辑大小上限，再安全转换为数值供 wasm32
ABI 使用；超过上限返回明确的资源限制结果，不改变已有上传语义。每次
`offset/length`
校验整数、安全范围和加法边界；渐进轮次、窗口数、逻辑缓存字节和实际块读取分别计量。

物理读取预算必须在消费已知长度的块流前预留，流读取时继续校验实际长度；单次越界不能在整块分配后才被发现。已有 12
MiB 是物理块预算，不表示允许再无限增加逻辑窗口或全缓冲副本。

### R2：跨请求 Promise 排队不应成为调度器（高）

渐进读取包含多轮 D1/R2 异步等待。现有 HTTP 触发通过 `waitUntil`
执行，而后台延长期有限；[现有租约](../../../../../../apps/worker/src/previews.ts)为两分钟，并在领取时计入 attempts。直接把已领取任务挂在模块级 Promise 队列，会让等待消耗执行时间及重试配额；取消、超时也可能把队尾留在不可恢复的等待状态。单次本地并发成功不证明这些边界成立。

首版不在 isolate 内排跨请求等待队列：渲染器只做立即独占准入，忙碌返回内部
`deferred`，由原编排按租约围栏释放并延后任务，忙碌不消耗内容失败配额。任务排队、重试仍由现有 D1 行承担；不新增一份内存任务真相，也不在进入前保留整份 PDF 缓存。单 isolate 准入不是跨 isolate 全局限流。

异步读取设置总截止时间与请求预算，每个阶段检查；同步原生调用仍受平台 CPU 限制，不承诺计时器抢占。测试覆盖排队压力、截止时间、租约失效和先到请求结束，不能只测两个成功请求。

### R3：常驻回调表可能把源缓存留在内存中（高）

局部读取 PoC 每个请求
`table.grow(3)`，注册的回调闭包持有块缓存、窗口缓存和文件源；其安全前提是该请求的整个模块不再被保留。字体/内存 PoC 则复用常驻模块。若直接组合两者，只销毁 PDF 文档并不会移除函数表对回调的引用。

每个运行时只分配固定的桥接槽位，或用有界槽位复用；会话结束时先关闭可安全关闭的文档与 availability 句柄，再清除当前会话引用、缓存和回调数据。不得无限增长函数表或留下源 I/O 闭包。捕获原生 abort 后不能假定所有 native
cleanup 都安全，必须先标记运行时不可复用，避免清理异常遮盖原错误。

验收应观察长期重复任务下回调表容量有界、任务结束后无会话引用、源缓存归零，以及失败时的同样不变量，而不只观察 WASM 堆容量是否增长。

### R4：64 MiB 不是整个 preview 的内存保障（高）

复审读取现用 WebP 编码器 WASM 声明：初始 256 页，即 16
MiB，最大 32,768 页。PDFium 64 MiB 加编码器初始 16 MiB，再加最多 12
MiB 的块缓存及复制出来的逻辑窗口，已经可能接近平台预算；字体文件、临时像素、现有 Worker 和其他请求仍在外部。故障重建又可能让旧、新 PDFium 实例短暂共存。

完整组合的资源验证必须前移到实施完成门槛，不能等接受实施后才首次发现方案超预算。独占运行前建立统一内存账本，限制各缓存及编码过程；优先复用已验证数据、及时释放逻辑窗口。分配失败时隔离运行时，并对重建和反复失败设置有界策略；不能把置空引用等同于即时释放。

同 Worker 方案只有在组合压力和故障恢复验证通过后才可采用；否则暂停该执行路径并明确调整执行隔离方案，不允许靠放宽限制掩盖问题。模块化只降低替换成本，不宣称等同于物理内存隔离。

### R5：全量与局部一致，仍可能同时漏内容（中）

两个对比路径使用同一个 PDFium 配置，PoC 明确关闭了表单字段渲染；同一错误可以产生相同像素哈希。缺字可能只影响一小段文字，不能用“非白像素 >
0”证明可信；纯白首页又可能合法。

为第一页静态内容定义支持矩阵：普通页、旋转/CropBox、嵌入图片和已验证字体需有独立的预期输出；表单、XFA、缺少静态外观或无法覆盖的字体不能仅因渲染 API 返回成功而归为已支持。对已识别的不支持内容明确降级；不承诺识别任意字体缺失。不得为了补字段执行文档脚本或加载外部资源。

保留局部/全量等价测试，但同时加入独立参考渲染或人工确认的固定样例。输出完整首页像素不代表卡片完整展示：[现有卡片样式](../../../../../../apps/web/src/styles.css)使用居中
`cover`。首版保持现有卡片裁切语义并明确测试；不为本需求全局修改图片样式。若后续要求整页可见，再单独定义最小展示差异。

### R6：复用生命周期不等于只增加分派分支（中）

提高全局 `PREVIEW_VERSION`
会使其他格式的当前版本也变成缺失，不只是重新生成 PDF；浏览器仍可能短暂使用旧的
`unsupported` 缓存。旧产物在数据库保留，也不代表查询新版本 `pending`
时前端仍展示旧产物。原文“保留旧产物”仅承诺保留/回收语义，不新增“无闪烁旧图兜底”能力。

现有 `failed` 描述不再由卡片轮询，后端仍可能按退避重试；故忙碌和继续等待应映射为
`pending`/延后，而不是普通内容失败。对需要重试的暂时错误应明确恢复可见性，不用“后端会重试”代替 UI 验证；必要的 UI 修复必须只针对该状态转换，不能趁机重构所有预览。

版本上线测试覆盖重生成流量、缓存过期、后台成功后的刷新，以及账户节点、公开出版物和路径节点入口。确定性的密码/不支持/资源限制不应无意义重试三次；用已有状态和说明表达区别，不新增公开 PDF 专用协议。

### R7：PoC 证据要在实施中变成可复现测试（中）

现有文档保存了关键数字和方法，但实验脚本仍在会话目录，且使用独立本地依赖。它们是可行性证据，不是随仓库构建可复现的验收。实施必须固定合法样例、确定性生成器、原始与重建 WASM 校验、字体授权、回调 ABI 和完整组合测试；依赖更新要重跑这些检查。

R1 至 R4 是进入实施时首先验证和封装的边界；R5 至 R7 是交付和回归的必要范围。均不要求现在把 PDF 逻辑侵入存储、前端和账户系统。

## 平台依据

- [Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)：内存限制按 isolate 而非单请求计算，包含 JavaScript 与 WASM；`waitUntil`
  不能无限延长 HTTP 后台工作。
- [Workers 运行时错误说明](https://developers.cloudflare.com/workers/observability/errors/)：请求生命周期及 I/O 归属应由当前请求承担，不能把内存 Promise 链当作持久调度保证。
