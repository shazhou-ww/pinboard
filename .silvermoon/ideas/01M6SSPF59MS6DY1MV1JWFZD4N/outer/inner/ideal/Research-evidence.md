# PDF 缩略图调研证据与局限

本文支持 [Idea](./Idea.md)
与[技术方案](./Technical-proposal.md)，记录 2026-11-06 至 2026-11-07 已完成的隔离 PoC，不是业务实现或生产验收证据。实验程序和原始产物保留在会话目录，本文件持久记录关键方法、结果及未证明事项；不将实验脚本、依赖或字体二进制直接提交为生产代码。

## 验证环境与范围

- Windows，Node.js
  24.12.0，项目已有 Miniflare 驱动的真实本地 workerd，不是仅在 Node.js 中模拟 PDF 解析。
- Worker 兼容日期 `2026-10-14`，开启 `nodejs_compat`；PDFium 包
  `@hyzyla/pdfium@3.0.0`。
- WebP 使用项目已有 `@jsquash/webp@1.5.0` 编码器，WASM 通过预编译模块加载。
- 字体与内存实验执行了 45 项断言，包含顺序重复渲染、并发串行化、分配失败和故障恢复；韩文空白被作为已知限制记录，不算字体成功。
- 局部读取实验直接打包当时工作树的
  `content.ts`、`storage.ts`，应用仓库 D1 迁移，以本地 R2 实例存取真实 CAR；不是直接对内存 PDF 做虚假 Range 统计。
- 原实验业务代码基线为 `d3ccdb1`。整理文档时已快进到
  `86c976686739b5c88b7d26ecf1cce459d16a048d`，核对了读取链路相关差异；没有将所有实验在新 primary 和生产环境重新执行。

## 内存硬上限和恢复

使用 `wabt@1.0.39`
解析 PDFium 模块，将原来的初始 287 页、最大 32,768 页改为初始 287 页、最大 1,024 页；每页为 65,536 字节。重建后执行 WABT 验证与
`WebAssembly.validate`。

| 项目                       | 精确记录                                                           |
| -------------------------- | ------------------------------------------------------------------ |
| 初始线性内存               | 18,808,832 字节                                                    |
| 原最大线性内存             | 2,147,483,648 字节                                                 |
| 新最大线性内存             | 67,108,864 字节，即 64 MiB                                         |
| 原模块 SHA-256             | `beeaf5bbff216d555fecec7cd486072838c4632a2272d31b52ef1fd05008fe7c` |
| 限制后模块 SHA-256         | `bf0ce69582119820d3c59df02d2068fd111808844b772c27c527b347084552fc` |
| 限制后 WASM 文件大小       | 5,298,232 字节                                                     |
| 限制后 WASM 独立 gzip 大小 | 2,471,896 字节                                                     |
| 字体独立 gzip 大小         | 2,326,711 字节                                                     |

已验证可增长到恰好 64 MiB，再增长一个 64
KiB 页会被 VM 拒绝；申请 67,108,865 字节原生分配失败且可观测。

另一个 PDF 的压缩页面内容展开到 80
MiB，在约 65,273,856 字节堆容量时触发增长失败和原生 abort。继续复用该实例会使后续正常文件也失败；丢弃故障实例并重建后，正常文件成功，堆容量回到 18,808,832 字节。

上述数值是 PDFium 线性内存容量，不是总 isolate 峰值；gzip 数值是模块独立压缩结果，不代表业务 Worker 的部署计费包体积。没有证据证明故障后旧实例已立即被垃圾回收。

## R2 局部读取：精确比较

PDFium 的 `FPDFAvail` 返回下载提示，JavaScript 异步补充 64
KiB 文件窗口；同步回调只访问缓存。窗口读取映射为 UnixFS 区间，完整块经 CID 校验后进入去重缓存，包括共享进行中的读取 Promise。

局部与全量方式分别从新的请求内缓存开始，均通过同一存储层读取；统计实际 R2 块载荷字节，而非仅统计交给 PDFium 的窗口长度。以下四个文件均不是线性化 PDF。

| 样例                           |  文件字节 | 局部逻辑字节 | 局部 R2 字节 / GET 次数 | 全量 R2 字节 / GET 次数 | R2 节省 |
| ------------------------------ | --------: | -----------: | ----------------------: | ----------------------: | ------: |
| 两页合成文档，第二页携带大图片 | 5,761,061 |      124,965 |             519,290 / 3 |          5,762,170 / 23 |  90.99% |
| 上游四页文档                   |   338,715 |      207,643 |             338,823 / 3 |             338,823 / 3 |      0% |
| 上游单页图片文档               | 1,587,724 |    1,587,724 |           1,588,080 / 8 |           1,588,080 / 8 |      0% |
| 单块内嵌中文字体文件           |     2,662 |        2,662 |               2,662 / 1 |               2,662 / 1 |      0% |

四组局部与全量第一页 RGBA 的 SHA-256 分别完全相同：

| 样例                 | 两种方式相同的像素 SHA-256                                         |
| -------------------- | ------------------------------------------------------------------ |
| 两页合成文档         | `bb86bfc63b5ee7d5894e97f20f6cd21175d36e5a9e2917f3f733dc74902a8423` |
| 上游四页文档         | `7fc2ca45ad28a662553182aa8fc127030cf7598be3ffdd5054f8ea61b75f115b` |
| 上游单页图片文档     | `b70a27f44db2595cbabfed03eada20aa4f815356c817e24d1bad59b38f69914b` |
| 单块内嵌中文字体文件 | `ed12453662efee9b35311d93ce3ec4cc3e0afa8c78e807697ad44136492130a4` |

两页合成文件的第一页只有文字和色块，第二页引用 2400 ×
2400 的随机灰度图片；普通尾部 xref 指向对象。其较大资源与首页无关，因此适合检验跳过无关块，但不是全部现实 PDF 的收益预测。

上游样例来源为
[PDFium 包测试数据](https://github.com/hyzyla/pdfium/tree/v3.0.0/test/data)中的
`test_1.pdf` 和 `test_3_with_images.pdf`；密集字符测试来自
[PDF.js 的公开回归文件](https://github.com/mozilla/pdf.js/blob/master/test/pdfs/perf_text_cjk_nonembedded.pdf)。合成中文字体文件和随机图片在实验本地生成，正式测试需固化确定性生成器与合法字体来源，不依赖会话路径。

## 已验证的失败与发现

- 将实际读取预算压低到 100 字节时，读取明确失败，不继续生成。
- 修改本地 R2 中 CAR 的根块载荷后，因 `Block bytes do not match CID`
  拒绝生成；没有省略完整块验证。
- 未合并进行中读取时，单页图片样例发生重复下载，R2 读取量一度比全读高约 82.5%；将缓存改为共享 Promise 后恢复为与全读相同。这是必须保留的回归场景。
- 渲染期间未出现未缓存同步读取，计数均为 0；遇到此情况的适配策略是明确失败，不能交付部分数据或空白填充。

## 明确未验证

没有在生产 R2、正式发布版本或真实用户文件上运行；没有执行生产上传或部署。局部读取实验验证的是第一页像素与存储读取，字体和 WebP 流水线在另一组实验中验证，不能声称完整组合已经完成业务端到端验收。

尚缺完整业务接入后的资源压力、线上 CPU 与后台时限、部署总包体积、旧布局与复杂 DAG、表单及注释等变体、长期原生实例稳定性、字体缺失可观察性及权限回收回归。

因此结论是“具备可实现的技术路径”，不是“任意 PDF 都能少量读取”或“64
MiB 上限已解决整个 Worker 的所有资源风险”。

## 2026-11-07 架构复审补充

本次按[架构设计与复审](./Architecture-review.md)复核方案，业务代码仍未实施。检查基线为
`f03488a59476a88dfb13d4e417eca3b06bb919de`；该次 primary 更新未修改 PDF 方案或 Worker 存储/预览链路。

- 只读尺寸探针：同一个 1 MiB
  raw 叶块被 UnixFS 根重复引用 64 次，只有两个唯一块、总载荷 1,051,786 字节，但 exporter 报告逻辑文件大小为 67,108,864 字节。证明去重 DAG 的上传字节限制不能替代 PDF 逻辑大小检查；未进行生产上传。
- WABT 检查现用
  `webp_enc.wasm`，内存声明为初始 256 页、最大 32,768 页，即初始 16
  MiB。PDFium 的 64 MiB 上限不覆盖该编码器、JavaScript 缓存与字体文件系统。
- 静态复核：渐进 PoC 在每次请求中扩展三个函数表槽位并闭包捕获源缓存；另一 PoC 复用全局渲染实例。不能把两种生命周期直接组合后声称缓存会随文档销毁。
- 静态复核：现有租约领取会增加 attempts；前端仅轮询 `pending`，`failed`
  可由后台重试但不会自动继续同一轮卡片轮询。新准入和错误分类必须针对这些现有行为测试。
- 静态复核：PDFium 包当前普通页面渲染带注释标志，但 PoC 未启用表单字段渲染。相同配置的局部/全量哈希一致不能证明表单、缺字等内容完整；现有卡片还会居中裁切图片。

这些是已核实的输入事实和由此产生的实现风险，不代表已经完成常驻运行时泄漏复现、全部表单正确性测试或线上资源验收。
