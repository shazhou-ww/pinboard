# Deployment

## Steps

### D-S01: 确认验证环境与回退边界

在得到明确环境授权后安排发布与远端验证，确认现有内容保留、索引兼容和回退条件；保持默认关闭推送部署，不擅自发布生产环境。

实现验收后先由单独授权的 D1 操作者核查生产现有 schema 和迁移记录，再仅补充
`0002_car_storage.sql` 的 CAR 表及索引；已手工初始化的旧库不可盲目重放
`0001`。沿用 release
tag 工作流，不把迁移或权限扩展加入发布流水线。新数据写入后旧 Worker 无法读取 CAR-only 内容，回退须保留 CAR 读取能力，以前向修复为默认；不得为回退永久双写全部独立块。具体操作见
`docs/deployment.md` 的 CAR rollout prerequisite。

### D-S02: 验证真实 R2 下载与性能

在获授权环境对相同多小文件样本和多块大文件进行单块、整包及旧内容下载验证；在相同条件下重复测量旧/新存储读实现的首字节时间、总耗时、对象请求数及存储字节数，并注明缓存状态和样本规模。原生产时点缺失的固定样本基线不得补造；用户现已另行授权当日隔离真实 R2/D1 的同条件复现实验，按
[隔离实验协议](IsolatedComparison.md)执行，明确区分实验和生产历史。

### D-S03: 清理临时实验资源

先持久化原始证据，再仅删除本实验明确新建的 Worker、R2 桶、D1 库及临时凭据，以控制面复核清理结果；不得删除生产或其他会话资源。出现未知内容、资源身份不一致或权限不足时停止破坏性动作并记录恢复条件。

CID；在全新离线 Kubo 仓库导入下载 CAR、重建并逐文件比较 SHA-256；单独保留原生产非空 legacy

## Acceptance criteria

### D-AC01: 远端内容可用且完整

以已保留的生产新旧内容证据，以及临时真实 R2 中两种表示的下载、独立 CID 校验与离线 Kubo 逐文件重建，证明内容完整且单块范围读取正确。实验 seeding 只使用同一固定样本的两种物理表示，不伪造用户身份或生产数据。

### D-AC02: 性能与空间取舍可核查

保存同一隔离 Worker/runtime/依赖、同一组固定样本、同一客户端条件下的真实 R2 旧/新读实现对照，证明新格式整包下载不再逐块读取，并报告首字节时间、总耗时、实际对象字节及新增索引空间；对任何性能退化给出明确结论，不以本地模拟替代真实 R2 证据，也不把当日实验宣称为原生产时点的历史数据或完整旧应用重放。
